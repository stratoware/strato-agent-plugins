# Design Element authoring

Design Elements explain the technical solution and architecture in more depth than the linked specifications. Describe the relevant component responsibilities, interfaces, data or signal flow, mechanisms, and design choices with their rationale. Add the detail needed to understand how the requirements are realized; avoid repeating the specifications or cataloguing every source file and implementation detail.

Normally use a couple of short paragraphs and one focused diagram. An architectural overview may need modestly more explanation to cover system boundaries and subsystem interactions. Use Markdown and fenced Mermaid for diagrams, or supported engineering artifacts where appropriate. Keep the diagram focused on technical structure or behavior.

Use code, schematics, drawings, and technical documentation as design evidence. When repository documents mix engineering content with delivery planning, extract only the supported technical design. Exclude implementation status, completion percentages, schedules, milestones, release slices, roadmaps, to-do lists, backlogs, task ownership, and development sequencing from Design Element titles, descriptions, and diagrams. Report alignment findings in chat and handle any selected delivery work through the agreed project workflow.

Organize Design Elements around coherent technical concerns, not repository planning documents or release increments. A design may explain several specifications; link the relevant records rather than duplicating the explanation. Do not infer technical decisions from task labels or fill missing design detail with guesses. Raise unresolved design questions in chat.
